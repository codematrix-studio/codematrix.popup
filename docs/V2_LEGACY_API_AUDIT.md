# Аудит legacy API V2

Дата проверки: 2026-11-20  
Ветка: `v2/d7-migration`  
Репозиторий: `codematrix-studio/codematrix.popup`  
Базовое окружение стенда: PHP 8.2.30, Bitrix main 26.150.0.

## Назначение

Документ фиксирует инвентаризацию оставшихся вызовов legacy API после переноса операций с собственными таблицами модуля на D7 ORM.

Цель миграции — не механически удалить все старые классы Битрикс, а заменить те API, для которых есть подходящий D7-аналог без изменения поведения. Контракты административного интерфейса, компонентов, установщика, AJAX и формат хранимых настроек должны сохраняться.

На этом этапе выполнен первичный статический просмотр исходников ветки. Это не заключение о полном отсутствии других legacy-вызовов и не результат runtime-тестирования.

## 2. AJAX и совместимость контрактов

Проверены точки входа:

- `admin/codematrix_popup_ajax.php` — обработчики `getPopups`, `getBasket`, `getTemplatePath`, `getHTML`, `statisticShow`, `statisticTime`, `statisticAction`.

- `install/components/codematrix/popup.pro/templates/*/ajax.php` — AJAX-файлы шаблонов.

В административном AJAX используются `Application::getInstance()->getContext()->getRequest()`, но сериализация ответа пока выполняется через `CUtil::PhpToJSObject()` с дополнительной заменой кавычек. Это требует отдельного анализа: нельзя заменять JSON-сериализацию, пока не зафиксированы фактические ответы и ожидания JavaScript.

Нужно сохранить имена действий, параметры, структуру ответов, кодировку, обработку ошибок и статистические события.

## 3. API, которые не следует заменять автоматически

- `CModule` в установщике — базовый механизм жизненного цикла модуля.
- `CBitrixComponent` и `CAdmin*` — штатные контракты компонентной и административной подсистем.
- `CDBResult` — пока используется как адаптер для совместимости административной навигации с результатом ORM.
- Legacy API без прямого D7-эквивалента с идентичным контрактом нельзя заменять формально только ради удаления старых имён.

### Работа с файлами в административной части

- Получение списка файлов модуля в административном AJAX-обработчике переведено с `CFile::GetList()` на `Bitrix\\Main\\FileTable::getList()`.
- Сохранены фильтр по `MODULE_ID`, сортировка по `ID DESC` и используемые поля `ID`, `SUBDIR`, `FILE_NAME`.
- `CFile::Delete()` оставлен намеренно: удаление файла должно сохранять штатную обработку записи `b_file`, физического файла и связанных механизмов ядра. Замена на `FileTable::delete()` или `Bitrix\\Main\\IO\\File::delete()` неэквивалентна и может оставить неконсистентные данные.

### Преобразование ID файла в публичный путь

В `classes/general/popup.php` оставлены два вызова `CFile::GetPath()`:

- при подготовке свойств выбранного шаблона в `getTemplates()`;
- при формировании свойств попапа в `getHTMLByPopup()`.

Это не выборка данных для ORM: метод ядра разрешает ID файла в путь, используемый шаблонами и фронтендом. Прямая сборка пути из `FileTable` (`/upload/{SUBDIR}/{FILE_NAME}`) не является гарантированно эквивалентной для конфигураций с внешним/облачным файловым хранилищем и может изменить URL. Поэтому вызовы оставлены как совместимый файловый API ядра; замена без отдельного теста на конфигурации хранилища не производится.

Проверены остальные основные PHP-точки модуля, включая компоненты, AJAX-шаблоны и установщик: дополнительных вызовов `CFile` для чтения/записи файлов в них не обнаружено. `CFile::Delete()` в административном AJAX-обработчике также оставлен для штатного удаления файла.

В `MakeTimeStamp()` по-прежнему передаётся формат именно текущего сайта; сама функция преобразования оставлена без изменений, поскольку здесь мигрируется источник настройки, а не формат хранения значения.

Сохраняются выборка незакрытой корзины текущего сайта, состав `products`, расчёт суммы как `PRICE * QUANTITY` и отдельное добавление ID родительских товаров для SKU.

`CCatalogSKU::getProductList()` оставлен: актуальная документация Bitrix по-прежнему указывает его как API для разрешения связей торговых предложений с родительскими товарами; прямой эквивалент на D7 ORM для этой операции не подтверждён. ### Чтение правила скидки для купона

Это миграция чтения таблицы, а не переход на новый движок расчёта скидок. ### Сопоставление торговых предложений с родительскими товарами

В `classes/general/popup.php::GetBasketInfo()` вызов `CCatalogSKU::getProductList()` оставлен без замены. Он получает для массива ID торговых предложений соответствующие родительские товары и используется для сохранения прежнего состава списка товаров корзины.

Прямой эквивалент этой операции в `Bitrix\\Catalog\\ProductTable` не подтверждён: таблица предоставляет ORM-доступ к товарным параметрам, но сама по себе не выполняет сопоставление offer ID с parent product ID. Документация Bitrix по `CCatalogSKU::getProductList()` описывает именно это пакетное сопоставление; актуальное руководство по производительности также использует этот метод для получения родителей предложений. Поэтому механическая замена на ProductTable или чтение свойства привязки без учёта конфигурации SKU может изменить результат.

Решение: оставить штатный API каталога для специализированной операции, не затрагивая уже переведённую на D7 загрузку корзины. Runtime-проверка на стенде с SKU и обычными товарами остаётся обязательной.


Изменение загрузчика JS-зависимостей: `CJSCore::Init(['ajax', 'popup'])` заменён на `Extension::load(['ajax', 'popup'])` в `classes/general/popup.php::insertPopups()`. Документация Bitrix указывает, что `Extension::load()` регистрирует расширения и при успешной регистрации вызывает `CJSCore::Init()`; список зависимостей сохранён. Коммит кода: `bef9df056e6c3a8cbc91a422e961d3e8f9df88a1`. Требуется runtime-проверка на стенде, что BX.ajax и BX.PopupWindow доступны на публичной странице.
