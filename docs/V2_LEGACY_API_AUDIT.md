# Аудит legacy API V2

Дата проверки: 2026-11-20  
Ветка: `v2/d7-migration`  
Репозиторий: `codematrix-studio/codematrix.popup`  
Базовое окружение стенда: PHP 8.2.30, Bitrix main 26.150.0.

## Назначение

Документ фиксирует инвентаризацию оставшихся вызовов legacy API после переноса операций с собственными таблицами модуля на D7 ORM.

Цель миграции — не механически удалить все старые классы Битрикс, а заменить те API, для которых есть подходящий D7-аналог без изменения поведения. Контракты административного интерфейса, компонентов, установщика, AJAX и формат хранимых настроек должны сохраняться.

На этом этапе выполнен первичный статический просмотр исходников ветки. Это не заключение о полном отсутствии других legacy-вызовов и не результат runtime-тестирования.

## 2. AJAX и совместимость контрактов

Проверены точки входа:

- `admin/codematrix_popup_ajax.php` — обработчики `getPopups`, `getBasket`, `getTemplatePath`, `getHTML`, `statisticShow`, `statisticTime`, `statisticAction`.

В административном AJAX используются `Application::getInstance()->getContext()->getRequest()`, но сериализация ответа пока выполняется через `CUtil::PhpToJSObject()` с дополнительной заменой кавычек. Это требует отдельного анализа: нельзя заменять JSON-сериализацию, пока не зафиксированы фактические ответы и ожидания JavaScript.

Нужно сохранить имена действий, параметры, структуру ответов, кодировку, обработку ошибок и статистические события.

## 3. API, которые не следует заменять автоматически

- `CModule` в установщике — базовый механизм жизненного цикла модуля.
- `CBitrixComponent` и `CAdmin*` — штатные контракты компонентной и административной подсистем.
- `CDBResult` — пока используется как адаптер для совместимости административной навигации с результатом ORM.
- Legacy API без прямого D7-эквивалента с идентичным контрактом нельзя заменять формально только ради удаления старых имён.

### Работа с файлами в административной части

- Получение списка файлов модуля в административном AJAX-обработчике переведено с `CFile::GetList()` на `Bitrix\\Main\\FileTable::getList()`.
- Сохранены фильтр по `MODULE_ID`, сортировка по `ID DESC` и используемые поля `ID`, `SUBDIR`, `FILE_NAME`.
- `CFile::Delete()` оставлен намеренно: удаление файла должно сохранять штатную обработку записи `b_file`, физического файла и связанных механизмов ядра. Замена на `FileTable::delete()` или `Bitrix\\Main\\IO\\File::delete()` неэквивалентна и может оставить неконсистентные данные.

### Преобразование ID файла в публичный путь

В `classes/general/popup.php` оставлены два вызова `CFile::GetPath()`:

- при подготовке свойств выбранного шаблона в `getTemplates()`;
- при формировании свойств попапа в `getHTMLByPopup()`.

Это не выборка данных для ORM: метод ядра разрешает ID файла в путь, используемый шаблонами и фронтендом. Прямая сборка пути из `FileTable` (`/upload/{SUBDIR}/{FILE_NAME}`) не является гарантированно эквивалентной для конфигураций с внешним/облачным файловым хранилищем и может изменить URL. Поэтому вызовы оставлены как совместимый файловый API ядра; замена без отдельного теста на конфигурации хранилища не производится.

Проверены остальные основные PHP-точки модуля, включая компоненты, AJAX-шаблоны и установщик: дополнительных вызовов `CFile` для чтения/записи файлов в них не обнаружено. `CFile::Delete()` в административном AJAX-обработчике также оставлен для штатного удаления файла.

## 21. Безопасность AJAX и шаблонов публичных попапов

- текст сектора вставляется и читается через textContent, а не innerHTML;
- текстовые поля результата и формы экранируются в HTML-контексте;
- значения, передаваемые в query string AJAX-запроса, кодируются через encodeURIComponent(), ID попапа приводится к целому числу.

BUTTON_METRIC в рулетке, как и в контактных формах, остаётся доверенным административным JS-фрагментом и не должен быть доступен для редактирования недоверенным пользователям.

Проверка после изменений: все изменённые файлы повторно получены из ветки и сопоставлены с отправленным содержимым. PHP lint, проверка JS и runtime-тесты на стенде не выполнялись. Отдельно требуется проверить совместимость сохранённых настроек рулетки, особенно если в тексте сектора ранее намеренно использовалась HTML-разметка.

## 28. HTTP-метод публичных обработчиков выдачи купонов

Проверка вызовов показала, что шаблоны `coupon_type1`, `discount_default` и `roulette_default` отправляют AJAX-запросы методом POST, однако серверные обработчики не проверяли HTTP-метод. Кроме того, параметры читались через `$request->get()`, поэтому значения из query string могли использоваться даже при POST-запросе. Для этих обработчиков это важно: они создают купоны, могут регистрировать пользователя, менять состав списка рассылки и отправлять письма.

Исправлено:

- В трёх обработчиках добавлена серверная проверка `$request->isPost()`.
- В обработчиках `coupon_type1` и `discount_default` параметры теперь читаются только через `$request->getPost()`; шаблоны передают их в теле POST, а не в URL query string.
- В обработчике `roulette_default` весь двухэтапный протокол также использует только POST-поля.
- При любом другом методе возвращается HTTP 405; побочные действия не выполняются.

Ограничение: проверка HTTP-метода не заменяет полноценную защиту от CSRF и злоупотребления публичными акциями. Отдельно оценить необходимость ограничения частоты выдачи купонов и проверки Origin/SameSite с учётом конфигурации сайта.

Статическая проверка внесённого условия выполнена чтением исходников. PHP lint и интеграционные проверки на стенде остаются обязательными.


## 29. CSRF-защита административных операций

В административном endpoint `admin/codematrix_popup.php` изменяющие AJAX-команды удаления изображения, создания пользовательского шаблона и создания цветовой темы не проверяли CSRF-токен. Основная форма сохранения попапа также не содержала явного `bitrix_sessid_post()` и не проверяла токен перед вызовом `editPopup()`.

Исправлено:

- Для `del_img`, `add_custom_colortheme` и `add_custom_template` добавлена серверная проверка POST и `check_bitrix_sessid()`.
- В AJAX-запросы удаления изображения, создания шаблона и цветовой темы добавлен `BX.bitrix_sessid()`.
- В форму редактирования добавлен `bitrix_sessid_post()`; сохранение настроек выполняется только при валидном токене.
- При невалидной сессии сервер возвращает HTTP 403 и не выполняет операцию.

Проверка статическая. Требуется проверить в административном интерфейсе сохранение попапа, удаление неиспользуемого изображения, создание пользовательского шаблона и создание цветовой темы. Отдельно остаётся проверить CSRF-защиту операций копирования и групповых действий списка: они используют штатные механизмы CAdminList либо отдельную ссылку и не входят в этот патч.


## 30. Приём данных контактных форм только через POST

В `CodeMatrixPopup::executeComponent()` поля контактной формы ранее читались через `$request->get()`. Этот метод объединяет параметры запроса и позволял передать поля формы через query string. При наличии настроек отправки письма, сохранения заявки, добавления адреса в список рассылки или регистрации пользователя это открывало путь к запуску побочных действий GET-запросом.

Исправлено:

- Поля `NAME`, `EMAIL`, `LASTNAME`, `PHONE` и `DESCRIPTION` читаются только через `$request->getPost()`.
- Подтверждение возраста (`checked`) также читается только из POST.
- Штатные контактные шаблоны отправляют форму методом POST; их контракт не меняется.
- GET-параметры больше не могут сформировать заявку или инициировать перечисленные действия.

Это ограничение HTTP-метода, а не полноценная CSRF-защита публичной формы. Отдельно остаются актуальными антиспам, rate limit и оценка защиты от межсайтовой отправки с учётом публичного сценария формы.

Проверка выполнена статическим сравнением исходника до и после изменения и повторным чтением файла из GitHub. PHP lint и интеграционные сценарии на локальной BitrixVM не выполнялись.


## 31. CSRF-защита копирования и групповых действий списка

Продолжена проверка административного списка попапов. Копирование записи ранее запускалось ссылкой GET (`action_button=copy`), хотя операция создаёт новую запись и копирует настройки. Это позволяло инициировать изменение состояния обычным переходом по ссылке.

Исправлено:

- Действие копирования отправляется POST-формой с `bitrix_sessid()`.
- Сервер принимает команду копирования только через POST и проверяет `check_bitrix_sessid()`.
- ID исходной записи проверяется как положительное целое число.
- После копирования выполняется локальный редирект на новую запись; внешний `HTTP_HOST` больше не используется для построения адреса перенаправления.
- Перед `CAdminList::EditAction()` и `CAdminList::GroupAction()` добавлена явная проверка sessid для POST-запросов, содержащих поля редактирования или групповое действие.
- Устранён обход этой проверки через GET: признаки `action` и `FIELDS` определяются независимо от метода запроса; если изменяющие параметры пришли не через POST, запрос отклоняется до вызова `CAdminList`. Значения `action` и `action_target` для выполнения групповой операции читаются только из POST.
- После сохранения используется относительный URL текущей административной страницы; заголовок `HTTP_HOST` не участвует в формировании `Location`.

Статическая проверка подтверждает наличие токена в отправляемой форме и серверных проверок до выполнения мутаций. Не проверялись PHP lint, поведение CAdminList на установленной версии БУС и сценарии копирования/группового редактирования в браузере.

- `UnInstallDB()` безусловно выполняет `DROP TABLE` для `codematrix_popup`, `codematrix_popup_add_colors` и `codematrix_popup_add_templates`. Теряются настройки попапов, пользовательские темы и пользовательские шаблоны.
- `UnInstallFiles()` удаляет `/upload/codematrix.popup`. В этой директории могут находиться загруженные пользователем изображения и другие файлы, на которые ссылаются настройки попапов.
- `UnInstallPostTemplate()` удаляет все почтовые шаблоны с кодами событий `CODEMATRIX_POPUP_SEND_COUPON` и `CODEMATRIX_POPUP_ROULETTE_SEND`, а `UnInstallPostEvent()` удаляет соответствующие типы событий. Удаление выполняется по коду события, без отдельного признака авторства конкретного шаблона.
- В `DoUninstall()` не обнаружено ветвления по настройке сохранения данных; очистка выполняется всегда.

Это не дефект штатной процедуры полного удаления, если пользователь сознательно выбирает удаление всех данных. Однако отсутствие режима сохранения данных создаёт риск случайной потери пользовательских настроек и загруженных файлов при переустановке или диагностике.

**Изменения не вносились:** изменение поведения удаления затрагивает жизненный цикл и ожидаемую семантику деинсталляции. Требуется отдельное решение: добавить штатный шаг выбора «сохранить данные» / «удалить данные» и сохранять пользовательские файлы по умолчанию либо оставить полное удаление как единственный сценарий.

Проверка выполнена статическим чтением `install/index.php` и `lib/mail.php`. Удаление модуля на стенде не выполнялось.


## 33. Проверка типа и шаблона при сохранении попапа

В `popupEdit::editPopup()` тип попапа и имя шаблона напрямую использовались как ключи/значения для выбора структуры полей. Сервер не проверял, что присланный шаблон действительно входит в список шаблонов выбранного типа. При подмене POST-параметров код мог обратиться к несуществующему элементу массива, получить неопределённую структуру свойств и сохранить некорректную конфигурацию.

Исправлено:

- Тип сверяется с доступными типами, возвращаемыми `getTemplates()`.
- Шаблон ищется внутри списка выбранного типа; проверяется наличие массива `props`.
- При неизвестном типе или несовместимом шаблоне сохранение прекращается с ошибкой до формирования и записи настроек.
- Штатные и пользовательские шаблоны остаются допустимыми, если они присутствуют в списке доступных шаблонов для этого типа.

Проверка выполнена статическим чтением и повторным получением файла из GitHub. PHP lint и сохранение разных типов/пользовательских шаблонов в административном интерфейсе не выполнялись.


## 34. Безопасное чтение сериализованных данных

В чтении настроек попапов и пользовательских шаблонов ранее применялся `unserialize()` без ограничения допустимых классов. Это позволяло PHP восстанавливать объекты из содержимого БД, хотя контракт этих полей предполагает массивы.

Добавлен единый метод `LegacyRowMapper::unserializeArray()`: он запрещает создание объектов через параметр `allowed_classes => false`, принимает только строку и возвращает только массив с вложенными массивами, скалярными значениями и null. Объекты (в том числе __PHP_Incomplete_Class), ресурсы, некорректные, пустые и данные другого типа приводятся к пустому массиву. Глубина вложенности ограничена 64 уровнями. Вызовы в классе попапов, редакторе и административном списке переведены на этот метод. Для сценариев, где отсутствие настроек делает запись непригодной для показа или формирования результата, добавлены ранние проверки; при выводе списка сайтов пустое или повреждённое поле больше не вызывает предупреждение.

Формат сериализованных данных в БД не меняется. Существующие массивы продолжают читаться; сериализованные объекты намеренно не восстанавливаются. Проверка на локальной BitrixVM не выполнялась.


## 35. Проверка типов входных данных контактной формы

В публичной контактной форме значения полей поступают из POST-запроса и передаются в строковые функции (filter_var(), mb_convert_encoding()). Параметр запроса может быть не только строкой, но и массивом. Передача массива в поле EMAIL или NAME могла привести к TypeError на PHP 8 и оборвать обработку компонента.

Перед валидацией и преобразованием значение теперь проверяется через is_scalar(); массивы и объекты отклоняются с ошибкой соответствующего поля. Допустимые скалярные значения приводятся к строке. Обычная отправка строковых значений и числового телефона сохраняет прежний контракт.

Проверка статическая. Требуется включить в стендовый набор отдельный негативный запрос с массивом вместо EMAIL/NAME и убедиться, что компонент возвращает ошибку поля без HTTP 500. PHP lint и runtime-проверка не выполнялись.


## 36. Итоговый статический аудит перед стендовыми проверками

Проверка выполнена по текущему содержимому ветки `v2/d7-migration` на 2026-11-20. Из области проверки исключён каталог `source/skyweb24.popuppro/`; архивы не анализировались. Проверены основные потоки административного редактирования, публичного показа, контактных форм, купонов/скидок/рулетки, статистики, ORM-модели и жизненного цикла установки. Это статический аудит репозитория, а не подтверждение работы на конкретной конфигурации Bitrix.

### Зафиксированные результаты

- Собственные таблицы модуля читаются и изменяются через D7 ORM. Legacy-обёртки административного интерфейса сохранены там, где они нужны для совместимости с API административного ядра.
- Сериализованные настройки читаются через `LegacyRowMapper::unserializeArray()`. Создание объектов запрещено; структура проверяется рекурсивно, допускаются массивы, скалярные значения и null, глубина ограничена 64 уровнями.
- Сохранение контактной формы отделено от GET-параметров; POST-значения проверяются на скалярный тип до строковой валидации и преобразования кодировки.
- Изменяющие административные AJAX-операции, копирование попапа и групповые действия списка защищены POST и sessid.
- Публичные endpoints выдачи купонов, скидок и рулетки ограничены POST. Это не заменяет антиспам, rate limit и полноценную проверку CSRF.
- Проверка типа и шаблона перед сохранением попапа добавлена ранее; произвольная строка типа больше не должна попадать в сохранённую конфигурацию через штатную форму.
- Отправка Sender-контактов исправлена под фактическую ORM-схему установленной версии; успешная отправка и сценарии существующего/нового email подтверждены пользователем на локальной VM. Внешняя доставка письма отдельно не подтверждалась.

### Остаточные риски, которые нельзя закрывать только статическим просмотром

1. **Права административной части.** В проверенных административных точках входа не обнаружена явная проверка уровня прав именно модуля `codematrix.popup`. Доступ к административной области и права на чтение/изменение модуля — разные уровни. Перед production необходимо проверить группы с правами «только чтение» и отсутствие доступа; при необходимости добавить проверку прав модуля на входе и перед изменяющими действиями.
2. **Публичная статистика.** `admin/codematrix_popup_ajax.php` принимает публичные `statisticShow`, `statisticAction` и `statisticTime`; сейчас достаточно положительного ID и, для времени, положительного целого. Не проверяется, что попап действительно был выдан этому посетителю, а длительность не ограничена. Возможна накрутка/порча статистики прямыми запросами. Нужны проверка допустимого попапа, разумный предел времени и/или серверный маркер показа, а также оценка rate limit.
3. **Публичные операции с побочными эффектами.** POST-проверка coupon/discount/roulette и контактных форм не ограничивает частоту запросов. До production проверить повторные запросы, массовую отправку писем, создание купонов, регистрацию пользователей и добавление контактов в Sender/инфоблок. Нужны отдельные антиспам и rate limit меры, согласованные с допустимым пользовательским сценарием.
4. **Валидация сохранения административной формы.** В `popupEdit::editPopup()` часть полей конфигурации принимается напрямую из POST; массив вместо строки, некорректные даты/интервалы, чрезмерный `roulette_element_count`, некорректные ID инфоблока/почтового шаблона и недопустимые CSS-значения требуют негативных проверок. Штатная форма админская и защищена sessid, но серверная валидация должна быть завершена.
5. **Проверка целостности старых записей.** Для повреждённых или неполных сериализованных настроек часть чтений уже имеет защиту, но необходимо проверить поведение на старых записях с удалёнными шаблонами, правилами скидок, файлами и соглашениями. Не удалять такие записи автоматически.
6. **Деинсталляция.** Полное удаление уничтожает три таблицы, файлы в `/upload/codematrix.popup`, скопированные компоненты/ресурсы и почтовые шаблоны/типы событий по кодам модуля. Сценария сохранения данных нет. Это должно быть осознанным поведением, а не частью обычного обновления.
7. **Обновление схемы.** `InstallDB()` создаёт таблицы через `CREATE TABLE IF NOT EXISTS`, но отдельного механизма миграции существующей схемы и последовательных update-скриптов в просмотренном дереве не найдено. Для текущей миграции схема собственных таблиц не менялась; будущие изменения структуры потребуют отдельного upgrade-пути.
8. **Совместимость ID компонента.** `onPrepareComponentParams()` подставляет ID=1 при отсутствии `ID_POPUP`. Это исторический fallback; оставлен без изменения, поскольку его удаление может сломать старые подключения компонента. Проверить на стенде подключение без параметра и с несуществующим ID.
9. **Согласие.** Шаблоны контактных форм визуально задают checkbox согласия отмеченным по умолчанию. Серверная проверка факта передачи `use_consent=Y` присутствует, но предустановленная отметка требует отдельного юридического и продуктового решения. До его принятия поведение не менялось.

### Итог

Статические изменения по выявленным однозначным дефектам внесены в ветку. Оставшиеся пункты выше — не заявление о подтверждённых эксплуатационных сбоях, а риски/контракты, которые требуют проверки на BitrixVM или отдельного решения по безопасности и бизнес-логике. В частности, не считаем модуль готовым к production только на основании этой ревизии.

### Единый набор проверок на BitrixVM

1. PHP lint всех изменённых PHP-файлов; затем просмотр журнала PHP/Bitrix на warnings, notices, TypeError и ORM exceptions.
2. Открытие административного списка, сортировка, навигация, редактирование, создание, копирование, групповая активация/деактивация/удаление; повторить под пользователем с read-only правами модуля.
3. Сохранение корректных настроек каждого используемого типа попапа; негативно отправить массив вместо строковых полей, неверный ID, неверный тип/шаблон, некорректные даты и завышенное количество элементов рулетки.
4. Публичный показ: активный/неактивный попап, сайт, группы пользователя, диапазон дат, маски URL, число просмотренных страниц, повторный показ, таймер, отсутствующие файлы и удалённые шаблоны.
5. Контактная форма: GET не вызывает побочных эффектов; POST с корректными значениями; неверный email; массив вместо EMAIL/NAME; пустые обязательные поля; снятое/установленное согласие; повторная отправка; письмо, инфоблок, Sender и регистрация отдельно.
6. Купон/скидка/рулетка: POST и GET; действующее и удалённое правило скидки; новый и существующий email; корректный/неверный купон; повторный и параллельный запрос; отсутствие двойной отправки письма; ограничение частоты запросов.
7. Статистика: штатные показ/действие/время; прямой запрос с чужим/неактивным ID; нулевое, отрицательное и чрезмерное время; повторные запросы.
8. Согласие: корректный ID соглашения, несуществующий ID, фактическая запись согласия и URL источника.
9. Установка/переустановка/обновление/удаление только на копии сайта: наличие таблиц и событий после установки, сохранность пользовательских файлов, поведение повторной установки и ожидаемая полнота удаления.
10. Проверить все используемые шаблоны, включая custom templates/colors, и очистить кеш компонента после обновления файлов.

До завершения этого набора проверок считать ветку подготовленной к стендовому этапу, но не прошедшей его.


## 37. Перевод получения путей файлов на D7

В двух местах `classes/general/popup.php` использовался `CFile::GetPath()` для преобразования ID изображения в путь. Добавлен сервис `CodeMatrix\\Popup\\FilePath`, который получает метаданные файла через `Bitrix\\Main\\FileTable` и формирует прежний публичный путь вида `/upload/<SUBDIR>/<FILE_NAME>`. Оба вызова переведены на этот сервис; формат значения для шаблонов и сохранённых настроек не меняется.

Остальные файловые legacy-операции не заменялись автоматически: удаление файла через `CFile::Delete()` выполняет не только работу с ORM-записью, но и удаление физического файла. Для его замены сначала требуется отдельная проверка эквивалентного D7-контракта.

Проверка выполнена статически по текущим файлам GitHub. PHP lint и проверка фактического отображения изображений на BitrixVM не выполнялись.


## 38. Проверка прав административной части

В административных страницах списка/редактирования попапов и статистики добавлена проверка прав модуля через `$APPLICATION->GetGroupRight('codematrix.popup')`. Пользователь без доступа к модулю получает штатную форму отказа. Пользователь с правом только чтения может просматривать список и настройки, но не может выполнять копирование, изменяющие AJAX-команды, групповые операции или сохранять форму. Для изменяющих действий дополнительно сохраняется проверка POST и sessid.

Публичный обработчик `admin/codematrix_popup_ajax.php` намеренно не закрывался административными правами: он используется публичной частью сайта для показа попапов и сбора статистики. Его защита должна строиться на проверке публичного сценария, а не на правах административного пользователя.

Проверка выполнена статическим анализом и повторным чтением файлов из GitHub. Runtime-проверка под учётными записями с правами «нет доступа», «чтение» и «запись» остаётся обязательной на BitrixVM.


## 39. Проверка типов и ограничение входных значений административной формы

В `popupEdit::editPopup()` добавлены ранние проверки структуры POST-значений до их использования:

- тип и имя шаблона должны быть строками;
- цветовая тема должна быть непустой строкой;
- значения параметров шаблона должны соответствовать типу значения, заданному структурой шаблона (массив остаётся допустимым только для массивного параметра);
- временные границы и даты не принимают массивы/объекты;
- список товаров корзины должен быть массивом положительных целых ID; отсутствие выбора трактуется как пустой список;
- число элементов рулетки проверяется как целое от 1 до 100 до начала цикла;
- название попапа не принимает массивы и объекты.

Проверки прекращают сохранение с понятным сообщением вместо передачи некорректных структур в строковые функции, `foreach`, сериализацию или ORM. Диапазон рулетки ограничен 100 элементами для защиты от чрезмерного цикла при подмене POST.

Изменения проверены статическим сопоставлением фрагментов и повторным чтением файла из GitHub. PHP lint, корректное сохранение всех типов попапов и негативные POST-запросы остаются частью проверки на BitrixVM.


## 40. Итоговая классификация оставшихся legacy API

Повторный поиск по ключевым файлам основной логики, административной части, компонента, шаблона скидки и установщика после выполненных изменений показал следующие оставшиеся вызовы:

- `CSite::GetDateFormat()` и `MakeTimeStamp()` — сохранены вместе: формат даты зависит от настроек сайта, а текущий разбор даты является частью совместимого контракта административной формы. Переводить только получение формата на D7 без замены и тестирования парсера нельзя.
- `CIBlockElement::Add()` — используется для сохранения заявки в инфоблок. Замена на ORM должна отдельно учитывать события инфоблока, обработчики, свойства и результат добавления; без такой проверки оставлен штатный API.
- `CUser::SimpleRegister()` и `CUser::Update()` — участвуют в штатном сценарии регистрации и обновления профиля. Прямой `UserTable::add/update` не является эквивалентной заменой по побочным эффектам и событиям.
- `CFile::Delete()` — оставлен, поскольку операция должна удалить физический файл и связанные данные, а не только ORM-запись.
- `$DB->Query()` в `install/index.php` — используется для DDL в контракте установщика. Замена на D7 Connection не даёт самостоятельного выигрыша без отдельной проверки SQL-диалектов, движка, кодировки и повторной установки.

В проверенных основных классах `popup`, `popupEdit`, `Tools`, `Mail`, `FilePath`, `LegacyRowMapper` и классе установщика все найденные объявления методов имеют PHPDoc-блоки. Это статическая проверка наличия блоков; корректность каждого типа параметра и полнота описания побочных эффектов требуют отдельной ручной вычитки.

В двух основных классах `popup.php` и `popup_edit.php` после перевода получения путей файлов больше не обнаружены вызовы `CFile::GetPath()`, `CUser::GetList()`, `CGroup::GetList()`, `CIBlock*::GetList()`, `CSale*` или `CModule::IncludeModule()`. Оставшиеся legacy-вызовы выше сохранены по причинам совместимости, а не забыты.

Проверка выполнена по указанным ключевым файлам ветки. Это не утверждение об отсутствии любого legacy API во всех сторонних шаблонах и вспомогательных файлах; полный runtime-аудит и PHP lint выполняются отдельно.


## 41. Дополнительная проверка условий и таймера

В сохранении условий показа добавлена проверка типа для остальных полей: массивные значения допускаются только для условий, которые представлены массивом в текущей структуре (например, выбранные сайты и группы); скалярные поля не принимают массивы и объекты. Для параметров таймера добавлена такая же проверка до помещения значений в настройки.

Это дополняет проверку параметров шаблона, дат, интервала, списка товаров и количества элементов рулетки из раздела 39. Проверка не заменяет семантическую валидацию всех значений (например, соответствие выбранного ID существующему сайту/группе/инфоблоку); такие проверки и проверка реальных форм остаются отдельным этапом.


### Уточнение совместимости цветовой темы

Проверка цветовой темы допускает пустое значение для типов/шаблонов, у которых цветовая тема не предусмотрена. Если параметр не пришёл из формы, используется значение выбранного шаблона либо пустая строка. Массивы и объекты по-прежнему отклоняются. Это сохраняет возможность создавать баннеры, видео и другие шаблоны без цветовой схемы.


## 42. Проверка ссылочных значений административных настроек

При сохранении условий показа ID выбранных сайтов и групп теперь сверяются с текущим списком допустимых значений, сформированным ядром Битрикс. Контактные флаги принимают только штатное значение `Y`; при включении сохранения заявок в инфоблок проверяется положительный ID и фактическое существование инфоблока через D7 ORM.

Эти проверки дополняют типовую валидацию и не меняют штатные значения формы. Проверить сохранение настроек с реальными сайтами, группами и инфоблоками необходимо на BitrixVM.



## 43. Ограничение публичной статистики попапов

Публичные команды статистики в `admin/codematrix_popup_ajax.php` ранее принимали произвольный положительный ID существующей записи. Значение длительности `popupTime` полностью контролировалось клиентом. Это позволяло напрямую увеличивать счётчики чужих/неактивных попапов и передавать произвольное время.

Внесены следующие ограничения:

- При выдаче HTML попапа сервер сохраняет в сессии ID попапа и время выдачи. Маркер создаётся после проверки доступности попапа и вызова его компонента; если компонент не смог определить шаблон и вернул `false`, маркер не создаётся.
- Команды статистики принимаются только POST-запросами.
- Увеличение счётчика показов и целевых действий возможно только для попапа с действующим сессионным маркером выдачи HTML.
- Целевое действие и время учитываются только после зарегистрированного в этой сессии показа.
- Длительность рассчитывается по серверному времени начала показа; клиентское значение `popupTime` больше не используется. Для одной сессии длительность ограничена 24 часами.
- Маркеры выдачи старше 24 часов не принимаются.

Это не криптографическое доказательство фактического отображения окна: HTML попапа предварительно загружается на странице, поэтому посетитель технически может инициировать статистическую команду после получения HTML, не открывая окно визуально. Изменение закрывает прямую накрутку по произвольному ID и подмену времени, не меняя публичный контракт JavaScript-клиента и не вводя административную авторизацию.

Проверка выполнена статическим анализом клиентских вызовов в `script_public.js`, обработчика AJAX и метода `getAvailablePopups()`. PHP lint и сценарии показа/закрытия нескольких попапов, нескольких вкладок и длительного открытого окна должны быть проверены на BitrixVM.


## 44. Защита публичных операций от повторных запросов

Добавлен сервис `CodeMatrix\Popup\PublicRequestGuard`, который подключается через автозагрузку модуля и хранит краткосрочные маркеры успешных публичных операций в PHP-сессии.

Защита подключена к обработчику контактной формы и обработчикам купона, VIP-скидки и рулетки:

- успешный результат операции запоминается на 60 секунд;
- точный повтор того же запроса в пределах окна получает прежний результат: форма подтверждается без повторной отправки письма/записи в инфоблок, а купон не создаётся повторно;
- другой запрос к тому же попапу в пределах окна блокируется без выполнения побочных действий; для контактной формы выводится сообщение о временном ограничении повторной отправки, для купонных обработчиков возвращается штатная ошибка купона;
- для сравнения запроса используется SHA-256 от значимых параметров; email в сессии в открытом виде не сохраняется;
- ошибки валидации, отказ из-за уникальности email и неуспешное создание купона не фиксируются как успешная операция;
- старые записи защиты очищаются при последующих успешных операциях.

Ограничение действует в рамках одной PHP-сессии и не является полноценной распределённой защитой от ботов или запросов с разными сессиями/IP. Для межсессионного ограничения частоты потребуется отдельная политика на уровне сайта (например, D7 ManagedCache с учётом IP/пользователя и допустимых сценариев). Намеренно не вводился глобальный лимит, который мог бы блокировать разных посетителей одного NAT.

PHP lint и проверка повторного нажатия контактной формы, повторной отправки с теми же параметрами, смены email/результата рулетки и повторной попытки после истечения 60 секунд должны быть выполнены на BitrixVM.

## 45. Найденное ограничение защиты рулетки: результат выбирает клиент

При повторном просмотре `roulette_default` обнаружено отдельное важное ограничение, которое не закрывается `PublicRequestGuard`:

- JavaScript `roll_roulette_func()` самостоятельно выбирает сектор через `Math.random()` и после анимации отправляет его `rule` в `ajax.php`.
- Сервер сверяет переданный `rule` со списком призов, сохранённым в настройках попапа, и берёт текст результата из серверной конфигурации. Однако сервер не проверяет, что сектор действительно выпал случайным образом.
- Поэтому посетитель может вручную отправить POST с ID любого настроенного приза, в том числе наиболее ценного. Защита повторов ограничивает частоту в рамках одной сессии, но не подтверждает честность выбора и не препятствует выбору другого приза после окончания окна блокировки.
- Параметр `resultText` клиента фактически не используется для выбора текста, что правильно, но само значение `rule` остаётся доверенным входом.

На момент выявления проблема не устранялась точечной проверкой: все варианты `rule` уже являлись допустимыми настройками, поэтому whitelist не мог устранить подмену. Требовалось изменить протокол рулетки так, чтобы сервер единолично выбирал сектор через `random_int()`, а запрос выдачи приза был одноразовым и связанным с конкретным серверным выбором. Это изменение выполнено; актуальная реализация описана в разделе 46.

До исправления обработчик проверял тип попапа, факт выдачи HTML в текущей сессии, совпадение срока `TIMING` с настройками, допустимость email и режима добавления в базу, но всё равно доверял присланному клиентом правилу. После изменения сервер больше не принимает от клиента правило, текст результата или срок действия: все эти значения берутся из серверных настроек и сохранённого выбора. Проверки типа попапа, сессионного маркера, email и режима добавления в базу сохранены.

**Статус:** проблема исправлена в серверном обработчике и JavaScript-шаблоне. Подробности реализации и оставшиеся проверки приведены в разделе 46. Runtime-проверка с реальными купонами до проверки на тестовом правиле не рекомендуется.


## 46. Серверный выбор результата рулетки

Устранена возможность подменить выигрыш через POST с произвольным ID правила скидки. Протокол рулетки разделён на два этапа:

1. Браузер отправляет серверу email и параметры списка рассылки. Сервер проверяет настройки попапа и допустимость email, после чего выбирает индекс сектора с помощью `random_int()`.
2. Сервер сохраняет в PHP-сессии выбранный индекс, правило и текст результата, хеш email, режим добавления в список, время выбора и случайный токен. Клиент получает только индекс сектора и токен. Повторный запрос draw с теми же параметрами возвращает сохранённый выбор независимо от времени ожидания; изменить сектор повторным запросом нельзя.
3. Браузер анимирует колесо до полученного сектора и отправляет токен для подтверждения результата. ID правила скидки и текст результата от клиента больше не принимаются.
4. Сервер сверяет токен, сессию, email и режим списка, после чего выдаёт только сохранённый сервером результат. Выбор хранится в сессии до успешного подтверждения; повторный запрос не создаёт новый результат.
5. Успешный ответ кэшируется механизмом `PublicRequestGuard`; повтор того же запроса получает тот же ответ без повторного создания купона или повторной отправки письма. Токен удаляется после успешной операции. После успеха в сессии устанавливается отдельный маркер завершения на `864000000` секунд (около 27,4 лет) — тот же срок, который задан существующей cookie `codematrixPopupFilling_*`; новый серверный выбор в этот период запрещён даже при прямом POST-запросе.

Для сектора «ничего» также требуется подтверждение серверного выбора; после него устанавливается cookie завершения показа. Для призов «победа» и скидочных правил сохраняется прежний вызов штатной логики отправки письма/создания купона. Параметры результата, присланные браузером в старом протоколе, больше не используются.

**Ограничения и проверки:**

- Выбор гарантированно выполняется сервером, но распределение вероятностей остаётся равномерным между элементами массива настроек; отдельные веса для призов в текущей модели не предусмотрены.
- Маркер выдачи HTML по-прежнему подтверждает загрузку разметки в сессию, а не факт визуального открытия рулетки.
- Токен привязан к текущей PHP-сессии, email и режиму добавления в список и хранится до успешного подтверждения результата либо окончания жизни PHP-сессии.
- Нужно проверить на BitrixVM все типы секторов: обычный купон, `win`, `nothing`; также повтор запроса draw, повтор redeem, подмену token/email, восстановление незавершённого выбора после закрытия вкладки и отказ создания купона.
- Сервер исключает только служебный ключ `count`, сохраняет исходный порядок элементов компонента и отклоняет повреждённую структуру вместо фильтрации отдельных секторов. На BitrixVM всё равно нужно проверить соответствие индекса анимации выбранному призу.
- PHP lint актуальных PHP-файлов после последних изменений не выполнялся. Ранее встречавшиеся в этом документе утверждения о выполненном локальном PHP lint и проверке JavaScript через Node.js не подтверждены журналом фактического запуска и не должны считаться результатами тестирования. Проверка синтаксиса PHP и JavaScript, затем функциональные сценарии на BitrixVM остаются обязательными.


## 47. Защита таймера от повреждённых старых настроек

В проверке доступности попапов и в подготовке результата компонента дата таймера теперь проверяется до вызова методов `DateTime`:

- значение должно быть строкой;
- дата должна соответствовать формату `d.m.Y H:i:s`;
- дополнительно учитываются ошибки и предупреждения парсера `DateTime::getLastErrors()`;
- попап с включённым, но некорректно настроенным таймером не попадает в список доступных;
- если повреждённая запись всё же дошла до подготовки шаблона, таймер отключается для этого вывода, а сайт не получает фатальную ошибку из-за вызова `getTimestamp()` или `diff()` на `false`.

Это защитная проверка старых/повреждённых записей и не меняет формат даты, который сохраняет административная форма. Требуется проверить на BitrixVM обычный таймер, истёкший таймер и запись с пустой/неверной датой.


## 48. Защита административных групповых действий от GET

Проверка списка попапов усилена: признаки массового изменения (`action` и `FIELDS`) ищутся во всём входящем запросе. При их наличии обработчик требует POST, право записи в модуль и действительный `sessid`. Это важно, поскольку `CAdminList::GroupAction()` и `EditAction()` используют параметры запроса и могут читать их из объединённого набора GET/POST.

Параметры, определяющие тип действия и область применения (`action`, `action_target`), в собственном коде обработчика читаются из POST. Запрос с признаками изменения через GET завершается ответом 403 до вызова методов списка.

Проверить на BitrixVM:
- групповое удаление/активацию/деактивацию с корректным POST и `sessid`;
- те же параметры через GET — изменение не должно выполняться;
- POST без `sessid` и пользователь без права записи — изменение не должно выполняться;
- обычную сортировку, фильтрацию и просмотр списка без мутационных параметров.


## 49. Валидация ID при удалении изображения из административной части

В AJAX-команде `del_img` ID файла теперь читается только из POST и проверяется как положительное целое до вызова `CFile::Delete()`. Дополнительно сервер проверяет, что файл принадлежит модулю, существует и не используется ни одним попапом. Некорректный ID даёт HTTP 400, отсутствующий файл — 404, используемое изображение — 409; эти значения не передаются файловому API.

Удаление по-прежнему выполняется через `CFile::Delete()`, поскольку оно отвечает не только за ORM-запись, но и за физический файл и связанные данные. Изменение сохраняет прежний формат успешного AJAX-ответа.

Проверить на BitrixVM удаление неиспользуемого изображения с корректным ID, отказ для нечислового/массивного ID, отказ для файла другого модуля, запрет удаления изображения, используемого попапом, и отсутствие изменений при GET или POST без `sessid`.


## 50. Проверка путей при создании пользовательских шаблонов и цветовых тем

Методы `popupEdit::setTemplate()` и `popupEdit::setColorTheme()` используют коды типа, шаблона и темы в путях внутри каталога компонентов. Добавлена проверка, что эти значения являются строками и содержат только буквы, цифры, дефис и подчёркивание. Имя создаваемого элемента также проверяется как непустая строка длиной не более 50 символов.

При создании цветовой темы путь нового CSS-файла теперь формируется через каталог исходного файла и имя `custom_<ID>.css`, а не глобальную замену фрагмента исходного пути. Это исключает влияние совпадений кода темы в других частях пути. Результаты ORM-добавления и обновления теперь проверяются до копирования; при ошибке обновления запись удаляется. Если копирование каталога шаблона или CSS не удалось, новая ORM-запись удаляется, а частично скопированный ресурс очищается.

Административный AJAX-контракт сохранён: значения создания пользовательских шаблонов и тем читаются только из POST, а запросы по-прежнему требуют право записи и `sessid`.

Проверить на BitrixVM штатное создание шаблона/цветовой темы, отклонение массивов и строк с точками/слешами, отсутствие создания файлов вне каталога шаблонов и корректную работу с уже созданными пользовательскими темами.


## 51. Сохранение результата публичной операции до дополнительных побочных действий

В обработчиках купона и рулетки ответ теперь фиксируется в сессионном кеше сразу после успешного создания/определения результата и до добавления контакта в список рассылки и установки cookie. Это уменьшает риск повторной выдачи купона при повторном запросе после сбоя на последующих шагах.

Создание купона и отправка настроенного письма остаются частью `getCoupon()`; полностью атомарно объединить операции Битрикс Sale, Sender и почтовых событий без отдельного механизма очереди нельзя. Поэтому проверка на стенде должна включать повтор redeem/coupon-запроса после успешной выдачи, а также сценарий недоступности Sender.


## 52. Безопасная область cookie-флага заполнения попапа

Cookie `codematrixPopupFilling_<ID>` используется как клиентский флаг и больше не получает домен из HTTP-заголовка `Host`. Для него применяется host-only область cookie: браузер ограничивает отправку текущим хостом, а некорректное значение с портом не попадает в атрибут Domain.

Изменение применено к контактным формам, дисконтной карте и рулетке. Флаг остаётся доступным JavaScript (HttpOnly не включён), поскольку он нужен клиентской логике.

Проверить на BitrixVM работу флага на основном домене и поддомене, а также отсутствие атрибута `Domain` с портом в заголовке `Set-Cookie`.


## 53. Серверная проверка согласия в AJAX выдаче дисконтной карты

В отдельном обработчике `discount_default/ajax.php` согласие теперь проверяется независимо от HTML-атрибута `required`: если в настройках попапа включено согласие и выбрано соглашение, сервер требует `use_consent=Y`. Шаблон передаёт состояние checkbox и показывает отдельное сообщение при отказе.

При подтверждённом согласии обработчик регистрирует его через `Bitrix\\Main\\UserConsent\\Consent::addByContext()` до создания пользователя и купона. Это закрывает обход клиентской проверки прямым POST-запросом.

Проверить на BitrixVM оба сценария: отмеченное согласие — выдача карты и запись в журнал согласий; снятая галочка или прямой POST без `use_consent=Y` — отказ без создания пользователя и купона. Если согласие отключено в настройках, выдача должна работать как раньше.


## 54. Проверка результата ORM при копировании попапа

Метод `popupEdit::CopyPopup()` теперь проверяет входной ID как положительное целое, ограничивает выборку одной записью и проверяет `isSuccess()` результата `PopupTable::add()` до возврата нового ID. При некорректном ID, отсутствии исходного попапа или ошибке ORM возвращается `false`, а не потенциально пустой ID.

Проверить на BitrixVM копирование существующего попапа с сохранением настроек, отказ для несуществующего/некорректного ID и корректную реакцию административного интерфейса на ошибку записи.


## 55. Экранирование пользовательских названий в административном редакторе

В `install/js/codematrix.popup/script.js` добавлено HTML-экранирование значений, которые попадают в динамически собранную разметку редактора шаблонов и цветовых тем. Экранируются имена пользовательских шаблонов/тем, подписи, значения полей и содержимое textarea. Заголовок активного шаблона выводится через `text()`, а новые option и ссылки после AJAX создаются DOM-методами, без склейки пользовательского имени в HTML-строку.

Это закрывает сценарий сохранённого HTML/JS в названии пользовательского шаблона или цветовой темы при последующем открытии административного редактора.

Проверить на BitrixVM имя шаблона и цветовой темы с символами `< > " '`, убедиться, что они отображаются как текст и не создают HTML-элементы/скрипты; отдельно проверить обычное создание и переключение пользовательских шаблонов.


## 56. Проверка имени шаблона в административном AJAX API

Команды `gettemplate` и `gettemplatepath` больше не передают параметр `template` напрямую в `IncludeComponent()`. Принимается только строковый код из латинских букв, цифр, дефиса и подчёркивания. Массивы, точки, разделители каталогов и прочие символы отклоняются с HTTP 400 до подключения шаблона.

Проверить на BitrixVM штатную загрузку всех используемых шаблонов, отказ для значений `../...`, абсолютных путей и массива вместо строки.


## 57. Проверка сохранённых параметров купона и рулетки

Публичные обработчики больше не приводят ID правила скидки к целому числу без предварительной проверки: положительный ID должен быть строкой или целым числом. Логические значения, массивы и дробные числа не принимаются как ID. В настройках срока действия допускается пустая строка (прежнее поведение без ограничения срока) либо положительное целое число дней; массивы, логические значения, произвольный текст, ноль и отрицательные значения отклоняются. В дисконтной карте ID группы проверяется отдельно: повреждённое необязательное значение не может превратиться в ID группы `1`. Маска купона должна быть строкой ограниченной длины.

Проверить на BitrixVM штатные сроки 30 дней и пустой срок, а также повреждённые настройки с массивом вместо ID/срока, отрицательным сроком и массивом вместо ID группы.
