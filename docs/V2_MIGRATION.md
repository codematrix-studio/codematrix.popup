# Версия 2.0 — план миграции на D7

## Назначение документа

Документ фиксирует план технической миграции CodeMatrix Popup на D7 1С-Битрикс. Цель — обновить внутреннюю архитектуру без изменения возможностей модуля, пользовательских сценариев, формата настроек и внешних контрактов.

Это рабочий документ: фактические решения, изменения, тесты и обнаруженные ограничения дополняются по мере выполнения этапов.

## Происхождение и исходный код

- Рабочий проект: [codematrix-studio/codematrix.popup](https://github.com/codematrix-studio/codematrix.popup).
- Исходный публичный репозиторий, код которого использовался при создании первой версии: [ASDAFF/fly.popup](https://github.com/ASDAFF/fly.popup).
- Зафиксированный снимок исходного репозитория на момент аудита: commit `0c0e9e7b1ae8c286174219bd13bb227cdb5c06c9` (ветка `master`, 16.01.2026).
- Базовая версия CodeMatrix Popup V1: commit `dcd0c5d4864e4a87c747ca86a4ca66dd246976f7` в ветке `main`.
- Ветка разработки V2: `v2/d7-migration`.
- Каталог `source/skyweb24.popuppro/` не является источником V2 и не переносится.
- Исходный репозиторий `ASDAFF/fly.popup` используется только как исторический источник и не изменяется.

При описании происхождения важно различать авторство исходного кода и выполненную адаптацию: V1 CodeMatrix Popup создана на основе кода репозитория ASDAFF/fly.popup с адаптацией идентификаторов, путей, ресурсов и документации под CodeMatrix Popup.

## Границы задачи

### Входит в V2

- Перевод внутренней архитектуры на D7 API.
- Введение пространства имён `CodeMatrix\\Popup` и PSR-4-подобной структуры классов в каталоге `lib/` с регистрацией автозагрузки средствами D7.
- Перевод доступа к собственным таблицам модуля на ORM D7.
- Устранение прямой работы с глобальным объектом `$DB` в бизнес-логике модуля.
- Приведение работы с запросами, контекстом, ответами, событиями, почтой и зависимостями к соответствующим D7 API там, где это не меняет внешний контракт.
- Обеспечение обновления V1 → V2 с сохранением существующих данных.
- Сохранение совместимости существующих административных страниц, компонентов, шаблонов, JS/CSS и AJAX-контрактов.
- Документирование каждого этапа, миграции данных и проверок.

### Не входит в V2

- Новые типы окон, условия показа, интеграции или статистические возможности.
- Изменение интерфейса и поведения существующих окон.
- Переработка дизайна административной части.
- Замена или обновление пользовательской jQuery-библиотеки без отдельной технической необходимости.
- Перенос каталога `source/skyweb24.popuppro/`.
- Изменения в репозитории `ASDAFF/fly.popup`.

## Правило функциональной эквивалентности

V2 должна сохранять:

1. Идентификатор модуля `codematrix.popup`.
2. Имена и параметры компонентов `codematrix:popup.pro` и `codematrix:popup.pro.timer`.
3. Имена событий, AJAX-действий, полей запросов и ответов.
4. Коды типов окон, ключи настроек и структуру сериализованных параметров.
5. Имена собственных таблиц и существующие данные.
6. Пути шаблонов, CSS/JS-ресурсов и пользовательских шаблонов.
7. Логику установки, обновления и удаления с корректным сохранением/удалением данных в соответствии с выбранным действием.

Любое отличие поведения считается дефектом миграции, пока не доказано обратное и не согласовано отдельно.

## Зафиксированное состояние V1

Базовый снимок: `dcd0c5d4864e4a87c747ca86a4ca66dd246976f7`.

Первая версия уже частично использует D7: в коде присутствуют `Bitrix\\Main\\Application`, `Context`, `Request`, `Cookie`, `Localization\\Loc`, `Loader`, `Page\\Asset`, `UserConsent` и ORM отдельных модулей Битрикс. При этом архитектура смешанная: D7 API соседствуют с устаревшими глобальными классами и прямыми SQL-запросами.

### Основные legacy-узлы, обнаруженные при первичном просмотре

- `include.php`: регистрация классов через `CModule::AddAutoloadClasses`.
- `classes/general/popup.php`: основной класс без пространства имён; прямой доступ к БД через `$DB`; `serialize()/unserialize()`; смешение бизнес-логики, выборок, подготовки данных и интеграций.
- `classes/general/popup_edit.php`: класс редактирования без пространства имён; прямые операции с БД; сериализация настроек; смешение сохранения данных и подготовки административных данных.
- `install/index.php`: установщик на `CModule`; создание и удаление трёх собственных таблиц через `$DB->Query()`; регистрация событий и почтовых типов/шаблонов через старые API; копирование файлов в публичные каталоги.
- `install/components/codematrix/popup.pro/class.php`: компонент на штатном `CBitrixComponent`, одновременно использующий D7 и старые API модулей пользователей/инфоблоков/почты.
- `admin/codematrix_popup.php`: крупная административная страница со смешанным использованием D7 Request и legacy API.
- `admin/codematrix_popup_ajax.php`: отдельный обработчик с D7 Request, но с ручной маршрутизацией и формированием JSON через строковые преобразования.
- `admin/codematrix_popup_stat.php`: отдельная страница статистики; её фактическое поведение необходимо проверять отдельно, не подменяя миграцию реализацией новых функций.

### Собственные таблицы V1

| Таблица | Поля |
|---|---|
| `codematrix_popup` | `id`, `sort`, `active`, `name`, `type`, `stat_show`, `stat_time`, `stat_action`, `settings`, `cont_iblock`, `cont_posttemplate` |
| `codematrix_popup_add_colors` | `id`, `template`, `name` |
| `codematrix_popup_add_templates` | `id`, `name`, `type`, `template` |

Это предварительная фиксация схемы по установщику V1. Перед созданием ORM-сущностей схема будет дополнительно сверена с фактической структурой таблиц на тестовом стенде и со всеми запросами к ним.

## Предварительная архитектура V2

Целевая структура (уточняется после инвентаризации зависимостей):

```text
lib/
  Popup.php
  PopupEdit.php
  Model/
    PopupTable.php
    PopupColorTable.php
    PopupTemplateTable.php
  Service/
    ...
  Event/
    ...
  Controller/
    ...
```

- `lib/Model/*Table.php`: ORM-сущности собственных таблиц модуля.
- `lib/Popup.php`: основная предметная логика.
- `lib/PopupEdit.php`: сценарии редактирования.
- `lib/Service/`: отдельные сервисы только там, где разделение уменьшает связанность и не меняет поведение.
- `lib/Event/`: обработчики событий, если это потребуется после проверки текущих контрактов.
- `lib/Controller/`: D7-контроллеры только при условии сохранения действующих URL, параметров и формата ответов.

Не следует механически переносить каждый старый файл в новый класс. Сначала фиксируются ответственность, публичные методы и все места вызова. Компоненты Bitrix остаются компонентами на штатном компонентном API; сам по себе переход на D7 не требует отказа от `CBitrixComponent`.

## Политика совместимости и данных

- Не переименовывать таблицы V1 и не удалять их при обновлении.
- Не менять типы и смысл полей без доказанной необходимости.
- Не менять структуру массива `settings` и ключи, используемые компонентами и шаблонами.
- На первом этапе ORM должна читать и записывать существующий формат данных без преобразования.
- Если потребуется изменение схемы, оно оформляется отдельным идемпотентным шагом обновления с проверкой старой и новой схемы.
- Удаление модуля и обновление модуля — разные сценарии. Обновление не должно вызывать `DROP TABLE`.
- Совместимость старых имён классов сохраняется через явно описанный адаптер/псевдонимы, если аудит подтвердит внешнее использование этих имён.
